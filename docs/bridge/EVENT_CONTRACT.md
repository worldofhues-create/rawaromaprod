## Envelope

Every event crossing the bridge, in either direction, is this shape on the wire:

```jsonc
{
  "event_id":       "uuid",       // minted once by the producer; the idempotency key
  "version":        1,            // monotonic per aggregate_id, starting at 1
  "type":           "ProductionRequirementCreated",
  "org_id":         "uuid",       // ALEMBIC tenant_id == RawProd org id for the bridge pairing
  "correlation_id": "uuid",       // ties every event on one requirement's journey together
  "causation_id":   "uuid|null",  // the event_id that directly caused this one, if any
  "occurred_at":    "2026-09-23T10:00:00.000Z",  // ISO 8601 UTC
  "source":         "alembic",    // "alembic" | "rawprod"
  "aggregate": {
    "type": "production_requirement",
    "id":   "uuid"
  },
  "payload": { /* event-type-specific, see below */ }
}
```

Field rules:

- `event_id` is a UUIDv4, minted by the producer and never regenerated by a relay or retry.
- `version` numbers the events for one `aggregate.id`, starting at 1, strictly increasing.
  A consumer that has already applied a `version` >= the incoming one treats the delivery as
  a duplicate or out-of-order and parks it (see Idempotency below) rather than applying it.
- `correlation_id` is the `bridge_production_requirement.correlation_id` for the whole
  lifecycle. Every event about one requirement — both directions — carries the same value.
- `payload` is an explicit, named-field object. **Never a formula, recipe, BOM, or any
  field from RawProd's `formula.*` schema.** This mirrors RawProd's own relay contract
  (`backend/api/src/relay/relay-contract.ts`, `isForbiddenAcrossGap`), applied to this
  second, non-air-gapped channel.

## Event types — ALEMBIC → RawProd

| Type | When | Payload |
|---|---|---|
| `ProductionRequirementCreated` | A commercial order line's mapped SKU has insufficient FG and no open requirement exists yet for it | `{ requirement_id, order_ref, mapped_sku, qty, uom, pack_size, needed_by, priority }` |
| `ProductionRequirementChanged` | Qty, needed-by, or priority changes on a requirement RawProd has not yet moved past `PLANNED` | `{ requirement_id, order_ref, mapped_sku, qty, uom, pack_size, needed_by, priority }` |
| `ProductionRequirementCancelled` | The originating commercial order is cancelled/returned before FG is allocated | `{ requirement_id, order_ref, reason }` |

## Event types — RawProd → ALEMBIC

| Type | Meaning |
|---|---|
| `ProductionRequirementAccepted` | RawProd validated the mapped SKU exists and queued it |
| `ProductionRequirementRejectedMapping` | The mapped SKU in the payload does not exist in RawProd's factory catalogue |
| `ProductionScheduled` | Entered a production plan |
| `ProductionStarted` | Mixing/production begun |
| `QcStatusChanged` | `{ qc_status: "pending"\|"passed"\|"failed" }` |
| `PackagingStarted` | Packaging begun |
| `FgBatchAvailable` | Finished-good batch produced |
| `AtpAllocationGranted` | FG allocated against this requirement |
| `DispatchReady` | Ready to ship |
| `Dispatched` | `{ awb, carrier, dispatched_at }` |
| `ProductionRequirementCancelledAck` | Acknowledges an ALEMBIC-initiated cancellation |

All carry `{ requirement_id }` at minimum, correlated by `correlation_id`.

## Transport

Signed HTTP webhook. Each direction is a separate connector, admin-configured
per-tenant/org through the existing self-service connector mechanism — **no
secrets in code, no `.env`, no redeploy to add or rotate one**:

- ALEMBIC side: `connector` row with `key = 'rawprod_bridge'`, non-secret
  `config.webhookUrl` (RawProd's inbound endpoint) and a sealed
  `connector_secret` (`field = 'hmac_secret'`).
- RawProd side: the mirror — an outbound webhook URL pointing at ALEMBIC's
  minted bridge endpoint, and the same shared HMAC secret, entered through
  RawProd's own connector-style admin config (not env vars, not a constant).

Request:

```
POST <configured webhook URL>
Content-Type: application/json
X-Bridge-Event-Id: <event_id>
X-Bridge-Signature: sha256=<hex hmac-sha256 of the RAW request body, keyed by the shared secret>
```

The signature is computed over the exact bytes sent — never a re-serialization
of the parsed body — so a receiver that re-encodes JSON differently than the
sender cannot false-negative a valid signature.

**Fail closed.** If either side's connector is not configured (no URL, no
secret): the sender leaves the event queued (`delivered_at IS NULL`) and never
sends unsigned; the receiver returns `401` for any request it cannot verify,
including when it has no secret configured at all — an unconfigured receiver
is not an open receiver.

## Idempotency, replay, ordering

- The receiver's primary key is `(tenant_id, event_id)`. A duplicate delivery
  (retry after a dropped 200, at-least-once redelivery) is a no-op insert; the
  receiver still returns `200` so the sender stops retrying.
- Ordering is per-aggregate only, via `version`. An event whose `version` is
  not exactly `last_applied_version + 1` for its `aggregate.id` is recorded
  (for audit/replay) but **parked**, not applied — `parked_reason:
  'out_of_order'` — until the missing version(s) arrive. This is a conscious
  simplification versus buffering/reordering: correctness over throughput,
  appropriate to this volume.
- Cancel is terminal: once `ProductionRequirementCancelled` is applied, any
  later-arriving event for that requirement other than
  `ProductionRequirementCancelledAck` is parked with `parked_reason:
  'unknown_aggregate'`-equivalent handling (aggregate exists but is closed) —
  see each repo's importer for the exact guard.

## DLQ / reconciliation

An event that fails delivery repeatedly (sender) or fails to apply after being
un-parked (receiver) is left in place with its failure recorded
(`last_error`, `attempts` on the sender; `parked_reason` on the receiver) —
both are queryable dead-letter views over the same tables, not a separate
DLQ table, so "what's stuck" is always one query against live state.
